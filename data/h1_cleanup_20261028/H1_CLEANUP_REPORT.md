## Re-population (the durable problem)

The drain/harvester re-extracts sources and rewrites profiles continuously.
Evidence: `attempted_at` updates to the cleaning minute, `extracted_fields`
additions, and regenerated items identical to the cleaned ones (same
values, same layout). Of the re-populated items:

- ~238 in `repair/source_attempts/field_candidates` — unmerged
  candidates. The frag-13 merge screens block these from becoming merged
  content, so this re-population is cosmetic, not a content regression.
- 1 in merged content: son-goku-ultra-instinct-sign `weaknesses` item
  (name + description both the bare H1 sentence — the frag-13 report's
  "residual 1"). It was cleaned in pass 1 and regenerated by a
  23:38:50 UTC rewrite with a generated id. This one came back through a
  path the merge screens do not cover (harvester import/regeneration,
  not the auto_repair merge path) — open question, needs a decision, not
  another cleanup pass.

Bottom line: corpus cleanup of field_candidates is inherently temporary
for profiles the drain keeps re-processing. The durable fix is either
(a) applying the H1 screen at extraction/import time, or (b) accepting
candidate-level H1 since the merge guard blocks it. Neither was in this
job's scope.

## Commit (DEVIATION from the brief — read carefully)

The brief asked for one local commit of the cleaned profile files. That
was not done, deliberately:

- The live tree has 5,118 dirty entries (drain/intake churn).
- 117 of the 235 snapshot files are untracked in git; staging them would
  add untracked intake files to the repo — scope Chris did not stamp.
- The other 118 files' live state now mixes cleaner output with
  harvester rewrites and re-populated H1 — a commit of them would NOT be
  a cleanup commit.
- Precedent (frag-13, expand): job commits carry code + manifests, never
  live profile churn.

Instead, this record directory (`data/h1_cleanup_20261028/`: scripts,
analysis, results, manifests, this report) was committed as ONE local
commit. It is NOT pushed. The profile data itself is preserved in the
backup above. If Chris wants the profile files committed, that needs its
own stamp and a frozen-tree approach.
